# 测试策略与完整回归清单

## 日常策略（按用户要求）

以后只测试与本次修改直接相关的关键功能及其必要依赖，不默认运行全量测试，也不默认每次使用 Chrome。完整清单保留为选测目录，不是每次发布的必做清单。

1. 开始修改前判断影响范围，选最相关的几项；功能未涉及的历史回归不重复执行。
2. 纯文档、文案：核对内容和链接；不跑游戏流程。纯文档提交不部署游戏。
3. 数值、战斗、掉落、物品事务：优先相关单元测试，必要时补一条实际游戏流程；不附带测试图鉴、商店等无关系统。
4. UI、原生弹窗、拖拽、层叠和布局：在真实 Google Chrome 检查相关界面、点击和截图。涉及 Firefox 等浏览器差异时，再测受影响的其他浏览器。Chromium 不等于完整的 Google Chrome。
5. 模型、镜头、动画：检查受影响模型的静止、运动、视角或遮挡；仅在相关逻辑变化时加对应单元测试，不自动测试仓库等系统。
6. 游戏代码发布保留类型检查与生产构建。已通过且未受新修改影响的测试不重复运行；失败后修复并重跑失败项及受修复影响的项。
7. 全量只在跨系统大改、核心架构/依赖/存档迁移等影响广泛，或无法合理界定风险时考虑执行。不要因为发布本身就运行全量。
8. 汇报明确区分实际通过、失败和未执行。保留现有断言，不靠忽略失败、禁用测试或重试掩盖问题来提速。

这套策略同步写入根目录 `AGENTS.md`，供后续开发读取。测试数量会随用例变化，本文的数量为编写时快照。

## “单元测试”和“浏览器全量测试”分别是什么

- 单元测试：Vitest 在 Node 环境调用游戏逻辑并断言结果，不启动浏览器、不访问公开网站。例如扣血、子弹守恒、仓库容量和存档恢复。此前报告的 74 项是当时数量；加入眨眼、相对方向动作与乡野地图回归后，当前为 **96 项**。
- 第一套浏览器全量：Playwright 在 GitHub Actions 临时机器启动 Vite 开发服务器，用 **Chromium** 执行全部 **50 项**浏览器用例。它不是在公开站点上测试。
- 第二套浏览器全量：相同 50 项在真实 **Google Chrome** 上再执行一次，用于查找曾出现的弹窗、图层等兼容问题。两套大量重复，日常不再默认执行。
- 公开站点完整验证：原有 `scripts/verify-production.mjs` 用真实 Chrome 操作 GitHub Pages 上的生产构建；日常不再重复运行，保留供按需回归。

## 静态网站为什么仍有部署差异

本项目是静态网站：GitHub Pages 托管 HTML、JavaScript、样式和资源，没有游戏业务后端，游戏逻辑在浏览器中执行。

开发测试访问 Vite 开发服务；发布访问经过类型检查、打包、资源重命名后的 `dist`。开发模式还有专门的测试接口，生产模式没有。即使本地使用 `preview` 验证同一份生产产物，也不能证明远程已经更新到这次提交。仓库子路径、资源上传、CDN 传播、浏览器旧缓存和 Service Worker 都可能造成差异。

因此日常线上只检查：`build.json` 提交号正确、入口 HTML、入口 JS/CSS、生成的 Service Worker 和其中列出的GLB模型可获取，模型文件头有效。脚本为 `scripts/check-published.mjs`，不启动浏览器、不操作角色、不重跑全量。它确认部署与入口资源可用，**不能据此宣称所有功能和旧缓存升级都验证通过**。仅在修改构建、资源路径、缓存或发布逻辑时，进一步检查相关的生产行为。

## 如何选择和执行

以下是命令示例，按实际修改选择其中几项，不要逐条全部执行。用例标题可从下方清单查找。运行前可用 `npx playwright test --list --grep '正则'` / `npx vitest list -t '正则'` 确认选中了哪些用例；零匹配不能算通过。

```sh
# 仅检查受击与搜索的逻辑
npm test -- tests/unit/raid.test.ts -t '受击.*搜索'

# 仅测试眨眼状态推进
npm test -- tests/unit/animation.test.ts

# 仅验证模型或镜头与搜索，不顺带执行图鉴、仓库等流程
npm run test:e2e -- tests/browser/cat-model.spec.ts tests/browser/camera-search.spec.ts

# 修改弹窗时，使用真实 Chrome，仅选相关用例
PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/google-chrome npm run test:e2e -- --grep 'Esc 菜单高于'

# 游戏代码变化后的类型检查与生产构建
npm run build
```

本机 Chrome 路径可能不同，应使用真实安装路径。Playwright 默认配置主要为 Chromium；Firefox 兼容验证需要实际启用 Firefox 的独立运行配置，不能把 Chromium 通过写成 Firefox 通过。

GitHub Actions 的 `Build, publish and check game`：

- 普通 `main` 推送：构建、部署、轻量线上检查；相关功能测试由开发时选测完成，不重复运行已验证流程。纯 Markdown / `docs` 修改不触发部署。
- 需要在 CI 执行相关测试时，手动运行 workflow，填写 `unit_pattern` / `browser_pattern` 标题正则，选择 `chrome` 或 `chromium`；留空不运行对应测试。
- 确实需要完整回归时，显式选择 `full_regression`，执行 96 项单元、Chromium 50 项、Chrome 50 项，以及原有完整线上验证。默认关闭。
- 原有 Chrome diagnostic 工作流是独立故障排查工具，仅修改其自身配置时触发，不随普通发布触发。

`game-workbench.spec.ts`使用Chrome检查当前数值、编辑/概率归一化/来源保护/完整及单独导出时间戳/往返、调音台嵌入和上传音量的实际总线、SC1解码、旧设置一次迁移，以及手机截图与存档隔离。生产构建用专项页面加载/试听与来源版本检查，不执行两套浏览器全量回归。
